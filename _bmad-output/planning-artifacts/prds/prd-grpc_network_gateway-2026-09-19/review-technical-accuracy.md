# Technical accuracy review — PRD vs repository

Reviewed 2026-09-19 against `HEAD` (4f5fa3f, branch `feat/containerise-and-health`). Scope: every FR tagged **[DELIVERED]** (FR-1, FR-2, FR-4, FR-5, FR-6, FR-7, FR-8, FR-9, FR-10, FR-11) plus addendum sections B and D. Files read: `src/main.rs`, `src/lib.rs`, `src/services/{gateway,health,mod}.rs`, `src/network/{router,mod}.rs`, `proto/gateway.proto`, `migrations/01_init_routing_table.sql`, `Dockerfile`, `compose.yaml`, `Makefile`, `kind/cluster.yaml`, `k8s/*.yaml`, `examples/*.rs`, `Cargo.toml`, `.sqlx/`, `.env.example`, `build.rs`, `init.sh`.

## Verdict

The delivered-FR section is unusually accurate for a PRD: the mechanism claims that carry the most weight for the operator's design — the `ON CONFLICT DO UPDATE` upsert, the Postgres-before-memory delete ordering, the lazy pool, the two independent health entries, the digest-pinned distroless image, the NodePort/host-port pairing, and the full pod hardening set — are all literally true of the code, at the lines cited below. Four claims are wrong or overstated, one of them materially: **FR-1 describes `CreateVpnTunnel` as if it had the same write ordering discipline the addendum credits `DeleteVpnTunnel` with, and it does not** — the in-memory insert happens *before* the database write, so a failed create leaves the serving pod's routing table holding a route that was never persisted. The rest are wording problems (a "single command" that is three, a bind address that *is* compiled in as a default, a "within one probe period" that the manifest's own `failureThreshold: 2` contradicts).

## False or overstated claims

- **[high]** **FR-1 / addendum D ("Upsert in `CreateVpnTunnel`") — write ordering is the *reverse* of `DeleteVpnTunnel`, and neither document says so.** The PRD's FR-1 consequence reads "A database failure returns `INTERNAL` and the call reports no success", which is literally true (`src/services/gateway.rs:92-94`) but hides the interesting half. `src/services/gateway.rs:79` inserts into the in-memory routing table **before** `src/services/gateway.rs:81-94` writes to Postgres. So on a database failure the caller gets `INTERNAL`, no row exists in `vpn_routes`, and the serving pod's routing table nonetheless holds the route — `RoutePacket` will answer `FORWARDED` (`src/services/gateway.rs:156-166`) for a tunnel that has no durable record, and `GetGatewayStatus` (FR-4) will list it, until that pod is replaced. This is exactly the divergence addendum D §"Write ordering in `DeleteVpnTunnel`" holds up as the reason delete is ordered Postgres-first ("The reverse order would produce a pod whose cache disagrees with the durable record until the next hydration") — create *is* the reverse order, and the addendum presents the ordering discipline as if it were uniform. It also sits badly against FR-4's consequence that `GetGatewayStatus` evidences "state lives in Postgres". Note the failure window is bounded in practice: hydration runs once and never re-runs after success (`src/services/health.rs:58,61-67`), so the stale entry survives for the pod's lifetime, not until the next resync.
  *Fix:* change the FR-1 bullet to "A database failure returns `INTERNAL`; the row is not persisted, but the serving pod's routing table has already been updated, so that pod's `GetGatewayStatus` and `RoutePacket` disagree with `vpn_routes` until it is rescheduled. `[NOTE FOR PM: `CreateVpnTunnel` writes memory-then-database, the reverse of `DeleteVpnTunnel` (FR-2). Reordering it to database-first is a small change and would make the ordering rule uniform — flag for `bmad-architecture`.]`" And in addendum D, retitle the ordering bullet "Write ordering" and state both directions explicitly.

- **[medium]** **FR-6 — "No connection string or bind address is compiled into the binary" is false for the bind address.** `src/main.rs:24-27` reads `BIND_ADDR` but falls back to a hardcoded `"0.0.0.0:50051"` when it is unset. Only `DATABASE_URL` is genuinely mandatory (`src/main.rs:29-31` returns an error when absent). `.env.example` reinforces the gap: it carries `DATABASE_URL` only, no `BIND_ADDR`. The claim is true of the connection string and false of the bind address.
  *Fix:* "No connection string is compiled into the binary — `DATABASE_URL` is mandatory and the process refuses to start without it (`src/main.rs:29-31`). `BIND_ADDR` is optional and defaults to `0.0.0.0:50051`, which is what the container and the `k8s/11-configmap.yaml` value both set explicitly anyway."

- **[medium]** **FR-10 — "A single command brings up a kind cluster running the Gateway, Postgres with a persistent volume, and the configuration they need" — there is no such command.** The `Makefile` has no aggregate target: `cluster-up` (`Makefile:53-55`), `load` (`Makefile:61-66`, which does depend on `image`) and `deploy` (`Makefile:68-70`) are three separate invocations, and nothing chains them. `.DEFAULT_GOAL := help` (`Makefile:4`) prints the target list. The consequence bullet ("A Makefile target set covers the whole loop") is accurate; the FR headline it sits under is not.
  *Fix:* either add a `make up: cluster-up load deploy` target and keep the sentence, or change the headline to "A small set of Makefile targets brings up a kind cluster running the Gateway, Postgres with a persistent volume, and the configuration they need."

- **[medium]** **FR-8 — "the pod leaves the Service endpoints within one probe period" understates it by a factor of ~3, and contradicts the PRD's own "~15s".** `k8s/30-gateway.yaml:88-94` sets `periodSeconds: 5` **and `failureThreshold: 2`**, so two consecutive failed probes are required — 10s of probing minimum. On top of that the readiness state itself only refreshes on the background loop's 5s tick (`src/main.rs:58` passes `Duration::from_secs(5)`; `src/services/health.rs:81`), and the pool is built with `PgPoolOptions::new().max_connections(5)` and no `acquire_timeout` (`src/main.rs:37`), so a `SELECT 1` against a vanished Postgres can block on sqlx's default acquire timeout before the loop can report NOT_SERVING. The third bullet of the same FR and addendum B's "~15s" are the honest numbers.
  *Fix:* "Readiness (`""`) reports NOT_SERVING whenever hydration has never succeeded or the database stops answering, and the pod leaves the Service endpoints within roughly 15s (a 5s health-loop tick plus `periodSeconds: 5` × `failureThreshold: 2`)."

- **[low]** **FR-8 / §3 Glossary — "Liveness is set SERVING once the server listens."** It is set SERVING at `src/main.rs:51`, *before* `Server::builder()...serve(addr)` at `src/main.rs:61-64`. Harmless in practice (nothing can probe a socket that is not yet bound), but the ordering claimed is not the ordering written, and if `serve()` ever failed to bind, the health entry would already say SERVING.
  *Fix:* "Liveness (`liveness`) is set SERVING as the server starts and is never touched again — `src/services/health.rs:72-73` writes only the `""` and the `GatewayControllerServer` entries."

- **[low]** **FR-2 — "never an error" is scoped tighter than it reads.** `DeleteVpnTunnel` parses `local_ip` as `Ipv4Addr` first (`src/services/gateway.rs:110-116`) and returns `INVALID_ARGUMENT` for anything that is not a dotted-quad IPv4 — including a valid IPv6 literal, which the `VARCHAR(45)` column (`migrations/01_init_routing_table.sql:3`) is sized to hold. A database failure returns `INTERNAL` (`src/services/gateway.rs:121`). The claim holds for the case it names (an *absent* tunnel with a well-formed IPv4 key and a healthy database), which is the case FR-18's finalizer hits given FR-13's IPv4 marker — but "never an error" is absolute wording for a conditional property.
  *Fix:* "Deleting an absent Tunnel returns `success=true, existed=false` — never an error, provided the local IP is a well-formed IPv4 address (FR-13 guarantees this at the CRD boundary)."

- **[low]** **Addendum D — "`hydrate()` replaces the table wholesale (`load_routes`) rather than merging, which is why it is safely retryable"** is true (`src/services/gateway.rs:41`, `src/network/router.rs:39-42`, `*write_guard = routes`) but the stated reason is slightly off: the wholesale replace is what makes it *idempotent*; what makes it *retryable* is that `load_routes` is only reached after `fetch_all` succeeds (`src/services/gateway.rs:26-28`, the `?`), so a failed query leaves the table untouched. Also worth recording: `src/services/gateway.rs:32` silently drops any row whose `local_ip` does not parse as IPv4, so the count logged at `src/services/health.rs:63` is routes applied, not rows read.
  *Fix:* "`hydrate()` builds the new map first and only then replaces the table wholesale via `load_routes`, so a failed query changes nothing and a successful one converges exactly on the database's contents. Rows whose `local_ip` is not IPv4 are skipped."

## Verified true

- **FR-1 — invalid `local_ip` returns `INVALID_ARGUMENT` and changes nothing.** `src/services/gateway.rs:66-72` parses before either mutation (`:79` memory, `:81` database), so the early return via `?` touches neither. Confirmed.
- **FR-1 / addendum D — the create is an upsert.** `src/services/gateway.rs:81-89`: `ON CONFLICT (local_ip) DO UPDATE SET tunnel_id = EXCLUDED.tunnel_id, remote_endpoint = EXCLUDED.remote_endpoint`, against the `UNIQUE` constraint at `migrations/01_init_routing_table.sql:3`. Re-applying an unchanged spec rewrites the same values and leaves `created_at` alone. FR-16's "a single create call handles both create and change" therefore holds.
- **FR-2 / addendum D — delete ordering is Postgres first, memory second.** `src/services/gateway.rs:118-121` executes the `DELETE` and propagates failure with `?` *before* `src/services/gateway.rs:124` calls `remove_route`. A failed database delete does leave a retry seeing an unchanged world.
- **FR-2 — absent delete is success.** `src/services/gateway.rs:123` derives `existed` from `rows_affected() > 0` and `:135` returns `success: true` regardless, with the rationale in the comment at `:133-134` and in `proto/gateway.proto:27-33`.
- **FR-4 — `GetGatewayStatus` returns the serving pod's in-memory table, not a cluster view.** `src/services/gateway.rs:185` reads `self.routing_table` via `get_all_routes` (`src/network/router.rs:44-47`), which clones the per-process `HashMap`. Addendum A.3's argument against using it for actual-state reads is well founded.
- **FR-5 — packet classification.** Match → `"FORWARDED"` with `bytes_processed` (`src/services/gateway.rs:158-166,174-177`); no match → `"DROPPED (NO_ROUTE)"` (`:167-170`); short or non-IPv4 header → `"DROPPED (MALFORMED_HEADER)"` (`:144-154` via `src/network/router.rs:50-58`). Both drops return `Ok`, not a `Status`.
- **FR-6 — both variables come from the environment, `.env` is optional.** `src/main.rs:24-25` (`BIND_ADDR`), `:29-31` (`DATABASE_URL`), `:22` `let _ = dotenvy::dotenv();` — the discarded `Result` is what makes a missing file a non-error. (See the FR-6 finding above for the `BIND_ADDR` default.)
- **FR-7 — the pool is lazy.** `src/main.rs:37`: `PgPoolOptions::new().max_connections(5).connect_lazy(&database_url)?`. No connection is attempted at construction.
- **FR-7 — hydration is retried by a background task and is idempotent.** `src/main.rs:53-59` spawns it; `src/services/health.rs:53-82` loops, calling `hydrate` until it returns `Ok` (`:61-67`), then switching to a `SELECT 1` liveness-of-the-database check (`:59`), sleeping `interval` between passes (`:81`). Idempotent by the wholesale replace at `src/services/gateway.rs:41`.
- **FR-8 — two health entries, genuinely independent.** `OVERALL = ""` and `LIVENESS = "liveness"` at `src/services/health.rs:30,41`; both set at `src/main.rs:49-51`. The readiness task writes only `OVERALL` and the `GatewayControllerServer` service name (`src/services/health.rs:72-73`) — `LIVENESS` appears nowhere in that loop, so liveness has no database dependency by construction, not merely by intent. `k8s/30-gateway.yaml:82-94` wires `livenessProbe` to `service: liveness` and `readinessProbe` to `service: ""`.
- **FR-8 — readiness starts NOT_SERVING.** `src/main.rs:49-50` sets both readiness entries NOT_SERVING before `serve()`, so no probe can observe SERVING before the first database check has actually run.
- **FR-9 — hermetic build.** `Dockerfile:26` sets `ENV SQLX_OFFLINE=true`; all three `query!` macro call sites have committed metadata in `.sqlx/` (the `SELECT`, the `INSERT ... ON CONFLICT`, and the `DELETE` — verified byte-for-byte against the source), and `.sqlx/` is git-tracked while `.env` is ignored (`.gitignore:2`). The health loop's `SELECT 1` uses the non-macro `sqlx::query` and needs no metadata.
- **FR-9 — both base images pinned by digest.** `Dockerfile:2` `rust:1.97-slim-bookworm@sha256:2775a09d…`; `Dockerfile:33` `gcr.io/distroless/cc-debian12:nonroot@sha256:9dac0a79…`.
- **FR-10 — the NodePort and the kind host mapping match, on loopback.** `kind/cluster.yaml:17-21`: `containerPort: 30051` → `hostPort: 50051`, `listenAddress: "127.0.0.1"`. `k8s/30-gateway.yaml:16`: `nodePort: 30051`. The pair is consistent, and the examples default to `http://127.0.0.1:50051` (`examples/smoke_client.rs:22`, `examples/health_probe.rs:18`), so host tooling needs no `port-forward`.
- **FR-10 — the claimed Makefile targets all exist.** `cluster-up` (`Makefile:53-55`), `cluster-down` (`:57-59`), `image` (`:47-49`), `load` (`:61-66`, depends on `image`), `deploy` (`:68-70`), `undeploy` (`:72-74`), `status` (`:76-78`), `logs` (`:80-82`), `smoke` (`:37-39`), `probe` (`:41-43`), plus `db-up`, `db-down`, `migrate`, `prepare`, `check`, `run`, `cluster-info`, `help`. Every target named in the PRD's bullet is present. (No aggregate target — see the FR-10 finding.)
- **FR-10 — topology.** Postgres is a `StatefulSet` (`k8s/20-postgres.yaml:18`) with `serviceName: postgres` behind a headless Service (`:9` `clusterIP: None`) and a `volumeClaimTemplates` PVC (`:69-77`); the Gateway is a `Deployment` (`k8s/30-gateway.yaml:19`) at `replicas: 1` (`:37`) behind the NodePort Service (`:7`).
- **FR-10 — `imagePullPolicy: IfNotPresent`** at `k8s/30-gateway.yaml:59`, with the no-registry reason in the comment at `:57-58` and `kind load docker-image` at `Makefile:66`.
- **FR-11 — the full hardening set is present.** Pod-level `runAsNonRoot: true` (`k8s/30-gateway.yaml:47`), explicit `runAsUser: 65532` / `runAsGroup: 65532` (`:50-51`), `seccompProfile: type: RuntimeDefault` (`:52-53`); container-level `allowPrivilegeEscalation: false` (`:97`), `readOnlyRootFilesystem: true` (`:98`), `capabilities: drop: ["ALL"]` (`:99-100`). All four items the PRD names, plus one it does not.
- **FR-11 — NetworkPolicies exist with an honest header.** `k8s/40-networkpolicy.yaml:1-19` states the non-enforcement plainly, names kindnet as the cause, and records the test that proved it; four policies follow (`default-deny`, `gateway-ingress`, `gateway-egress`, `postgres-ingress`). Consistent with §7 Non-Goals.
- **FR-3 is correctly tagged [NEW].** No `ListRoutes` / `list_routes` exists anywhere in `proto/gateway.proto` or `src/` — `proto/gateway.proto:4-9` declares exactly four RPCs. The PRD does not claim otherwise; confirming it so the epics do not assume a stub exists.
- **Addendum D — `src/lib.rs` exists and `main.rs` is a thin binary over it.** `src/lib.rs:7-8` exports `network` and `services`; `src/main.rs:9-16` imports from `grpc_network_gateway::`, and both examples link against the library (`examples/smoke_client.rs:9`). The stated reason (examples and `tests/` cannot link a binary target) is correct.
- **Addendum D — the Gateway runs no migrations; the schema is seeded via `docker-entrypoint-initdb.d`.** No `sqlx::migrate!` anywhere in `src/`; `k8s/12-configmap-initdb.yaml:15-22` carries the DDL and `k8s/20-postgres.yaml:50-52` mounts it read-only at `/docker-entrypoint-initdb.d`. The consequence the addendum draws — a missing table means readiness never flips — follows directly from `src/services/health.rs:58-68`, where `hydrated` can never become `true` if the `SELECT` keeps failing. The `migrations/` directory and `Makefile:21-23` `sqlx migrate run` are the host-development path only, consistent with the claim.
- **Addendum D — `examples/smoke_client.rs` walks create → observe → delete → confirm gone → delete again.** `examples/smoke_client.rs:25-59`, with assertions at `:38` (present after create), `:44` (`success && existed`), `:52` (absent after delete) and `:59` (`success && !existed` on the repeat). It is a faithful skeleton for FR-25 and FR-30. One caveat for whoever reuses it: the observation step uses `GetGatewayStatus`, which addendum A.3 correctly rules out as the reconciler's actual-state read — the example is a single-pod smoke test, not a template for FR-15.
- **Addendum D — `examples/health_probe.rs` mirrors a Kubernetes `grpc:` probe.** `examples/health_probe.rs:19` defaults the service name to `""` (the overall entry, what kubelet asks for when none is named), `:23-27` checks it, `:29-33` exits non-zero on anything but `SERVING`. `HEALTH_SERVICE` (`:19`) is what lets it query `liveness` too, which is how the split in addendum B could have been verified from the host.

- **§6 Constraints — every published port binds `127.0.0.1`.** `compose.yaml:9` (`"127.0.0.1:5432:5432"`) and `kind/cluster.yaml:20` (`listenAddress: "127.0.0.1"`). Both, with no exceptions in the repo.
