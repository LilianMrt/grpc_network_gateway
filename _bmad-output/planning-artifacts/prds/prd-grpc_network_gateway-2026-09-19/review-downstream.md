# Downstream readiness review — PRD to epics and stories

Reviewed against the actual contract of `.claude/skills/bmad-create-epics-and-stories/` (SKILL.md, `steps/step-01..04`, `templates/epics-template.md`, `customize.toml`), not against generic PRD best practice. Where a finding cites the skill, it cites the line that makes it a failure.

## Verdict

The PRD is unusually well-formed as a document — IDs are perfectly contiguous, every cross-reference resolves, and most FRs carry genuinely testable consequences — but it is **not consumable as-is** by this workflow, for two reasons that are structural rather than editorial. First, the workflow will not find it: both of step-01's PRD discovery globs miss the file's actual location, and its second required input (Architecture) does not exist at all. Second, and more damaging, the workflow's hard validation gate is "every FR appears in at least one story" (step-04 §1), and the PRD's §8.1 MVP In Scope explicitly lists FR-1 – FR-11 as in scope — so the workflow will dutifully generate eleven epics' worth of stories for work that already shipped, and its own success metrics will confirm it did the right thing.

If it runs as-is you get: a failed prerequisite check or a silent fallback to reading nothing; then, once pointed at the file by hand, an epic list that re-builds the delivered Rust gateway, misses or buries the one new Rust requirement (FR-3), orders the Helm epic before the Operator it is supposed to package, and produces two technical-layer epics (§4.7 Verification, §4.8 Observability) that step-02 names as SYSTEM FAILURE examples.

## Blocking issues

- **[critical]** **The workflow cannot discover the PRD.** (§ file location vs `steps/step-01-validate-prerequisites.md` §2) — Step-01 searches exactly two patterns: `{planning_artifacts}/*prd*.md` and `{planning_artifacts}/*prd*/index.md`. With `planning_artifacts = _bmad-output/planning-artifacts`, the first resolves to nothing (there is only a `prds/` directory) and the second would need `prds/index.md`, which does not exist. Verified: both globs return no match. The file is two levels deep at `prds/prd-grpc_network_gateway-2026-09-19/prd.md`. Step-01's failure mode here is not a clean error — it is "Missing required documents", listed under SYSTEM FAILURE, with no recovery path defined. *Fix:* add `_bmad-output/planning-artifacts/prds/prd-grpc_network_gateway-2026-09-19/index.md` containing a link to `prd.md` and `addendum.md` (this also satisfies the skill's "sharded" convention and pulls the addendum into `inputDocuments`), **or** symlink/copy the PRD to `_bmad-output/planning-artifacts/prd.md`. The index.md route is better because it is the only mechanism that gets the addendum loaded without the user remembering to name it at the "any other documents?" prompt.

- **[critical]** **`[DELIVERED]` is a label, not an instruction, and §8.1 actively contradicts it.** (§0 vs §4.1–4.3 vs §8.1) — The tag itself is per-FR, bold, and machine-greppable: 10 FRs carry it (FR-1, 2, 4, 5, 6, 7, 8, 9, 10, 11), and §0 explains they are "documented because the operator's design depends on their exact semantics, not because they are outstanding work." That explanation lives in §0 prose. What step-01 §3 actually instructs is "extract **ALL** functional requirements"; what step-02 §5 requires is a coverage map where *every* FR maps to an epic; what step-04 §1 enforces as a CRITICAL CHECK is "Go through each FR... Verify it appears in at least one story. **No FRs should be left uncovered.**" There is no `[DELIVERED]`, `status`, or "out of scope for stories" concept anywhere in the skill, template, or `customize.toml`. Worse, §8.1 "In Scope" reads: "The Gateway's control-plane API including the new `ListRoutes` (FR-1 – FR-5)", "Gateway runtime and health semantics **as delivered** (FR-6 – FR-8)", "Container image, kind cluster, manifests, pod hardening (FR-9 – FR-11)". A workflow that reads "MVP In Scope: FR-1 – FR-11" will build stories for FR-1 – FR-11. The two signals point opposite ways and the stronger-worded one (an explicit In-Scope list) wins. *Fix:* three changes, all cheap. (1) Add a `status:` line under each delivered FR heading with a literal directive the extractor cannot soften — `**Status:** DELIVERED — do not create a story. Recorded here for semantics the Operator depends on.` (2) Rewrite §8.1 to split "Already delivered (no stories)" from "To build (stories required)", moving FR-1, 2, 4–11 into the former and leaving FR-3 and FR-12 – FR-30 in the latter. (3) Add one sentence to §0 addressed at the consuming workflow: "For `bmad-create-epics-and-stories`: FRs marked `[DELIVERED]` are covered by shipped code; map them in the coverage map as `Delivered — no story` and treat that as satisfying the coverage gate." Without (3) the workflow's step-04 gate has no legal way to pass.

- **[critical]** **FR-12 and FR-23 are mutually forward-dependent — a circular epic dependency.** (§4.3 FR-12, §4.6 FR-23) — FR-12 requires "The Gateway, Postgres, **and the Operator** install into a cluster from one chart" and "The CRD ships in the chart's `crds/` directory". FR-23 requires "The Operator installs into the cluster as part of the same chart as the Gateway (**FR-12**)". Each is written as depending on the other. Compounding it, FR-12 sits in §4.3 Packaging alongside delivered FR-9 – FR-11 (early in the document) while FR-23 sits in §4.6 (late), so straightforward group-order reading puts the Helm chart epic *before* the Operator binary exists. Step-04 §5 makes this a CRITICAL failure: "Can Epic 2 function without Epic 3?" / "❌ WRONG: Story references features not yet implemented." *Fix:* make FR-12 gateway-and-CRD only ("the Gateway, Postgres, and the CRD install from one chart; the Operator's templates are added by FR-23"), and make FR-23 solely additive ("adds the Operator Deployment, ServiceAccount and RBAC to the chart defined in FR-12"). Then the dependency is one-directional: FR-13 → FR-12 → FR-23. Alternatively merge them into a single FR and a single epic, which is what I recommend in the decomposition below.

- **[high]** **FR-15 is an epic statement wearing an FR's clothes.** (§4.5 FR-15) — "Converge from any starting state" has four consequences that are not one story's work and are not disjoint from its neighbours: (a) fresh `ListRoutes` read every pass with nothing cached, (b) correct outcome from absent / present-but-wrong / already-correct, (c) idempotent across a hundred runs with no duplicated work, (d) a deleted VpnTunnel reconciles to a clean no-op. (b) and (c) are restatements of FR-16's diff-and-apply outcomes; (a) is the actual-state read mechanism; (d) is controller scaffolding. A single dev agent handed FR-15 either builds the entire reconciler (step-03: "❌ BAD: 'Build authentication system' (too large)") or writes a story whose ACs duplicate FR-16 and FR-17 verbatim. *Fix:* demote FR-15 to the **§4.5 feature-group description** — it is the epic goal statement, and reads perfectly as one — and split its content into two real FRs plus reassignments: **FR-15a "Reconcile the VpnTunnel resource"** (controller registered on the `VpnTunnel` kind; a `Get` returning NotFound produces a clean no-op return, not an error; every pass returns a `ctrl.Result` — consequence (d) and the scaffold), and **FR-15b "Read actual state fresh on every pass"** (calls `ListRoutes` (FR-3) at the top of every Reconcile; nothing about Gateway state is memoised between passes; the `UNAVAILABLE` case from FR-3 is propagated as an error rather than read as empty — consequence (a), and this is the one that carries the §5 cross-cutting NFR). Move consequence (b) onto FR-16 as its three cases (it already has two of them) and consequence (c) onto FR-24 as the named idempotency test it actually is.

- **[high]** **FR-3 is unambiguous in isolation but sits in a group the workflow will skip wholesale.** (§4.1) — FR-3's `[NEW]` marker is bold, unique in the document (it is the only `[NEW]` tag), reinforced by §8.1's "including **the new** `ListRoutes`", by §10 Q3 flagging it for architecture, by §11's assumptions index, and by the addendum's milestone table row "*(new, from the ListRoutes decision)* | FR-3". As an FR-level signal it is fine. The risk is the opposite of the one you asked about: FR-3 is FR number three of five in **§4.1 Gateway Control-Plane API**, where the other four are all `[DELIVERED]`. Step-02 designs epics from *feature groups* ("Look for natural groupings in the FRs"), and a workflow that correctly concludes "§4.1 is delivered, skip it" takes FR-3 with it. §4.1's own description — "The gRPC surface the Operator drives" — gives no hint that 80% of it is done and 20% is the single most load-bearing new requirement in the project. *Fix:* pull FR-3 out of §4.1 into its own feature group (e.g. "§4.1b Pod-Independent Actual State", or place it at the head of §4.5 Reconciliation where it is consumed), and add a line to §4.1's description: "Four of these five are delivered; FR-3 is the only new work in this group." Renumbering is not required — the FR ID stays FR-3, which §0 promises.

- **[high]** **The dependency graph that orders the epics exists only in the addendum, and even there it is incomplete.** (§4 group order vs `addendum.md` §E) — Three of the four orderings you named are only partly discoverable from the PRD:
  - **FR-3 → FR-15/FR-16: discoverable.** FR-15's first consequence literally says "reads actual state fresh from `ListRoutes` (FR-3)". Good.
  - **FR-13 (CRD) → the reconciler: NOT discoverable.** No FR in §4.5 (FR-15 – FR-20) cites FR-13 or FR-14 at all. FR-19 depends on FR-14's status subresource and does not say so. The only statements of CRD-precedence are FR-23's "The CRD is installed before the Operator starts" and FR-12's `crds/` consequence — both about *installation order*, neither about *build order*. Nothing stops the workflow putting Reconciliation before the VpnTunnel API.
  - **FR-21 (gRPC client) → FR-15/FR-16: NOT discoverable, and the group order inverts it.** FR-15 and FR-16 make `ListRoutes` and `CreateVpnTunnel` calls; the client that makes them is FR-21, in §4.6, *after* §4.5.   And the addendum's §E milestone table — the only complete ordering in either document — cannot rescue it, because §E itself assigns **no milestone** to FR-3, FR-17, FR-23, FR-1, FR-4 and FR-5, and the addendum is not discovered by step-01's globs anyway. *Fix:* add a **§4.10 Build Order** section to the PRD (not the addendum) stating the hard edges as a short list: `FR-3 → FR-15b`; `FR-13 → FR-14 → FR-15a`; `FR-21 → FR-15b, FR-16, FR-18`; `FR-13 → FR-12 → FR-23`; `FR-9 + FR-3 → FR-25`; `FR-15a..FR-20 → FR-24`. - **[high]** **Architecture.md does not exist, and the skill treats it as a required prerequisite.** (§ workflow step-01 §2, step-01 §5, step-04 §2) — Step-01's prerequisite list names "**Architecture.md** — Contains technical decisions, API contracts, data models" as item 2 of 3; step-01 §5 extracts "Additional Requirements" from it; step-04 §2 validates starter-template setup from it. ## Non-blocking issues

- **[medium]** **No NFR IDs anywhere.** (§5, §6, §7) — Step-01 §4 wants `NFR1: …`, `NFR2: …` and the template has an `{{nfr_list}}` slot. §5 Cross-Cutting NFRs is seven unnumbered bullets; §6 Constraints and §7 Non-Goals are unnumbered prose; §4.2 has an unnumbered "Feature-specific NFRs" paragraph under FR-8. - **[medium]** **Hyphenated IDs vs the skill's expected format.** (§4 throughout) — The PRD uses `FR-1`; step-01 §3 looks for `"FR1:", "Functional Requirement 1:", or similar` and formats output as `FR1: …`. "or similar" means extraction will work, but the *output* format in step-01 §3 and the coverage map in step-02 §5 both use the unhyphenated form, so `epics.md` will likely say `FR1` where the PRD says `FR-1`. Cosmetic until someone greps across the two. *Fix:* nothing in the PRD; worth telling the operator of the workflow to preserve the hyphen when it asks for confirmation at step-01 §9.

- **[medium]** **Three FRs are not completable by a dev agent, which the skill requires.** (§4.9 FR-28, FR-30; §4.7 FR-25 partially) — Step-03 §2 and step-04 §3 both require each story to "be completable by a single dev agent". - **[medium]** **FR-17's acceptance criterion cannot be written — its value is an open question.** (§4.17 third consequence vs §10 Q2) — "The interval is configurable and defaults to a value documented in the README" and §10 Q2 "What is the default resync interval (FR-17)? ... ## Proposed epic decomposition

The nine feature groups are a good *documentation* structure and a poor *epic* structure. Three of them (§4.1, §4.2, and two-thirds of §4.3) are essentially delivered; two of them (§4.7 Verification, §4.8 Observability) are technical-layer groupings that step-02 explicitly names as wrong epics; and §4.5, §4.6 and §4.8 all modify the same `operator/` files, which step-02 Step C and step-04 §4 flag as file churn requiring consolidation or justification.

**Groups that are bad epic boundaries:**

- **§4.1 Gateway Control-Plane API** — 4 of 5 FRs delivered. As an epic it is either empty or it rebuilds shipped Rust. Its one real requirement, FR-3, should stand alone.
- **§4.2 Gateway Runtime and Health Semantics** — 100% delivered. Not an epic. Zero stories.
- **§4.3 Packaging and Cluster Deployment** — mixes three delivered FRs with FR-12, which is new *and* depends on FR-13 and FR-23 from two later groups. The group's position in the document (early) is the opposite of FR-12's true position in the build order (late).
- **§4.7 Verification** — "Epic: Testing" is step-02's canonical SYSTEM FAILURE example ("❌ Epic 4: Deployment Pipeline (CI/CD setup) — No user value"). Worse, its FRs are pure forward dependencies: FR-24 tests behaviours from FR-15 – FR-19 and FR-25 tests FR-3 and FR-18, so as a standalone epic every one of its stories violates step-04 §5's "Story references features not yet implemented". Dissolve it into the epics whose behaviour it verifies.
- **§4.8 Observability** — two FRs, no independent user value, and both touch `operator/cmd/main.go` and the controller, which §4.5 and §4.6 also own. Consolidate.
- **§4.9 Repository Legibility** — a *good* boundary, and the one group that survives intact. Distinct files (README, `docs/adr/`, a recording), a distinct user (UJ-4's reviewing engineer), and real independent value. Keep it, but mark its stories manual-execution.

**Dependency order: E1 → E2 → E3 → E4 → E5 → E6.** Each epic uses only its predecessors' output and none requires a successor, satisfying step-04 §5.

**On the E3/E4 split and file churn:** both epics modify `operator/internal/controller/vpntunnel_controller.go`, which step-04 §4's File Churn Check will flag. The split is justified rather than incidental, and the justification should be recorded in `epics.md` so the check passes explicitly: E4 is a genuine feedback boundary — the resync interval (§10 Q2, still open) cannot be chosen sensibly until E3 has shown how long a converge actually takes, and the finalizer's add-before-create ordering is only testable once create exists. If you would rather avoid the flag entirely, merging E3 and E4 into one "The reconcile loop" epic with the same story order is defensible; it costs you the intermediate demoable state at the end of E3.

**On E5:** it exists as a separate epic from E3/E4 only because it touches a disjoint file set (`charts/`, `config/rbac/`, manifests) and because the Operator can be developed against envtest and `make run` out-of-cluster throughout E3 and E4 — FR-24 explicitly says "Tests run without a cluster." That is what makes E1–E4 shippable before any chart exists, and it is the fact that breaks the FR-12 ↔ FR-23 circularity in practice.
